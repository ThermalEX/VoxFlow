# VoxFlow 研究记录

本文档按时间汇总 VoxFlow 智能编辑（口语改写模型）研发过程中的设计决策、实验结果、遇到的问题与解决办法、得出的结论，以及后续改进方向，供日后撰写论文或报告时直接取材。工程交接细节见 [HANDOFF.md](../HANDOFF.md)，数据集原始设计见 [docs/superpowers/specs/2026-10-13-rewrite-dataset-design.md](superpowers/specs/2026-10-13-rewrite-dataset-design.md)。

**维护约定**：每做一次训练、评估、方案调整，或解决一个有代表性的问题，就在对应章节追加条目，并写明日期、数据版本和测试集版本。不同测试集上的数字不能直接比较，对比时只用同一份测试集。

## 1. 研究问题与系统概述

**问题**：语音输入得到的是“说出来的话”，而不是“想写下的文字”。口语里有口气词、重复、改口（“周五，不对，周六”），还有说到后面再回头修改前文的情况（“去掉苹果”）。用户还希望直接用语音下指令，比如“翻译成英文”“正式一点”。通用 ASR 只负责转写，不处理这些。

**目标**：在消费级笔记本（RTX 3060 Laptop，6 GB 显存）上本地运行一个小型改写模型，把 ASR 原始文本整理成最终要输入的文字，并给出可选的改写建议。不依赖云端，延迟要低到不影响输入节奏。

**系统流程**（2026-10-14 现状）：

```
麦克风 → SenseVoiceSmall（sherpa-onnx INT8，子进程）→ 实时草稿 / 最终文本
      → 任务 1 clean：清理 + 执行语音内联指令（llama-server 加载微调 GGUF）
      → 修改动画后显示整理结果，可撤回、悬停预览原文
      → 任务 2 suggest：后台生成 0–3 条改写建议（延迟 1.2 s 请求）
      → 用户确认 → 粘贴回原前台应用
```

模型通过 OpenAI 兼容接口调用，本地模型和云端服务可以在设置里互换。

## 3. 数据集

### 3.1 设计决策

| 决策 | 选择 | 理由 / 未选方案 |
| --- | --- | --- |
| 任务划分 | 一个模型、两个任务（clean / suggest），用不同系统提示区分，共用一个 LoRA | 两个 LoRA 维护和显存成本高；“规则清理 + 模型改写”无法可靠处理回头编辑（规则会误删正文） |
| 数据来源 | 人工撰写种子（由 Claude 在对话中撰写）+ 程序扩增 | 回头编辑、隐含理由的改口无法靠模板拼接生成，必须手写；口气词、重复、模板化即时纠正可以程序注入 |
| 指令位置 | 前置、后置约各一半，少量放在句中 | 用户实际说话时两种习惯都有（“翻译成英文：……”或“……，翻译成英文”） |
| 建议形式 | 自由方向、0–3 条，JSON 数组 `{label, text}` | 固定类别会产生无用建议；“好的”“收到”这类短句允许返回 `[]` |
| 反例 | 像指令的正文、中英混说、已经干净的句子，要求原样保留 | 防止模型过度修改，例如把“他让我把这段翻译成英文”当成指令执行 |
| 明确不做 | 同音错字纠正（“机器学系”→“机器学习”） | 小模型纠错容易凭空编造内容 |
| 划分 | 按种子分组，训练 85% / 验证 5% / 测试 10%；扩增变体随种子归组；测试集只含手写样本 | 杜绝泄漏，测试更接近真实说话 |

任务 1 覆盖 14 类：口气词、重复、即时纠正、回头删除 / 替换 / 补充、带理由的隐式修正、口述格式、翻译指令、风格指令、指令与编辑组合，以及 3 类反例。详见设计文档第 3 节。

构建脚本会自动做质量把关：字段与类别合法；建议条数 0–3、标签不超长；反例输出除标点外必须与输入一致；非反例输出不得残留指令词。任何一项不过，构建失败。

### 3.2 版本演变

| 版本 | 日期 | 手写种子 | 新增内容 | 测试集（清理 / 建议） |
| --- | --- | --- | --- | --- |

**撰写注意（经验）**：

- 避免用名人做样本。例如“周杰伦”的惯用英文名是 Jay Chou，按规则写成 Jielun Zhou 反而是错的，这类样本已删除。
- 避免凭名字推断性别。“黄晓雯老师”不译成 Ms.，“解晓明”不用 his。

## 4. 模型与训练配置

**模型选择**：基座为 Qwen3.5-2B，由用户指定候选 Qwen3.5 2B / 4B，先只训 2B。选择理由：

- 同尺寸下中文能力强，中英混说和互译是本任务的核心。
- 尺寸在 6 GB 显存可微调的范围内。
- 许可宽松。

模型自带“思考模式”，需要关闭。

| 超参数 | 取值 |
| --- | --- |
| 方法 | bf16 LoRA（Unsloth 官方文档不建议对 Qwen3.5 做 QLoRA 4-bit 训练：其量化误差高于常规模型） |
| LoRA rank / alpha / dropout | 16 / 16 / 0 |
| 目标模块 | q/k/v/o_proj，线性注意力层的 in_proj_qkv、in_proj_z、out_proj，MLP 的 gate/up/down_proj（Qwen3.5 是混合注意力架构） |
| 可训练参数 | 约 1560 万 |
| 学习率 / 预热 | 2e-4 / 20 步 |
| 轮数 | 2 |
| 批大小 | 1 × 梯度累积 8 |
| 最大长度 | 1024 |
| 优化器 | adamw_8bit；Unsloth 梯度检查点 |
| 对话模板 | `enable_thinking=False`，结束符 `<|im_end|>` |
| 随机种子 | 3407 |

| 版本 | 步数 | 训练用时 | 训练损失 | 验证损失* | 峰值显存 |
| --- | --- | --- | --- | --- | --- |
| v1 | 约 680 | 32 min | 0.245 | 0.2234 | 4.4 GB |
| v2 | 698 | 41 min（与其他程序争用 GPU，期间爆显存一次，见 §7） | 0.133† | 0.2027 | — |
| v3 | 726 | 44.5 min | 0.243 | 0.1975 | — |

\* 各版本的验证集随种子增加而变化，验证损失只能看趋势，不能严格比较。
† v2 从第 200 步续训，Trainer 只统计了续训部分的平均损失，因此偏低，不能和其他版本比较。

**导出**：在 WSL 中合并 LoRA，用 llama.cpp `convert_hf_to_gguf.py` 转成 GGUF（Q8_0、BF16），再在 Windows 上用 `llama-quantize.exe` 量化为 Q4_K_M。文件大小：Q8 2.0 GB，Q4 1.3 GB，BF16 3.9 GB。

## 5. 评估方法

脚本为 `training/rewrite/evaluate.py`，支持直接加载 HF 模型，也支持通过任意 OpenAI 兼容接口评估（`--endpoint`）。

| 指标 | 任务 | 含义 | 设计目标 |
| --- | --- | --- | --- |
| 完全一致率（exact） | clean | 规范化后与参考答案完全相同 | 横向对比 |
| 字符错误率（CER） | clean | 与参考答案的字符编辑距离 / 参考长度 | 越低越好 |
| 反例保留率 | clean | 3 类反例输出与输入一致（忽略标点） | ≥ 95% |
| 指令残留率 | clean | 输出仍含“翻译成英文”“去掉”等指令词 | ≤ 2% |
| 新增数字率 | clean / suggest | 输出出现输入中没有的数字（事实编造的代理指标） | ≤ 1% |
| 翻译 chrF | clean | 翻译类样本与参考译文的 chrF（sacrebleu） | 横向对比 |
| JSON 合法率 / 规则合规率 | suggest | 可解析、条数 0–3、标签合规、无重复 | 100% |
| 条数一致率 | suggest | 建议条数与参考一致（衡量“该少给时少给”） | 横向对比 |
| 延迟中位数 | 全部 | 单句端到端耗时 | ≤ 1 s |

**补充测试**：

- 姓名抽查：用训练种子里没有出现过的名字检查英译的名姓顺序和拼音。
- 端到端测试：把文字注入真实应用的浮层，检查修改动画、建议按钮，以及进程能否正常退出。

**局限**：风格改写和翻译的完全一致率不能代表质量，一句话可以有多种正确写法，需要人工评审。测试集规模也偏小（约 90 条清理），一条样本就相当于约 1% 的差异。

## 6. 实验结果

### 6.1 微调效果（测试集 v1：88 条清理 / 44 条建议）

| 指标 | 基座 Qwen3.5-2B（未微调） | 微调 v1（HF，bf16） | 目标 |
| --- | --- | --- | --- |
| 完全一致率 | 21.6% | **54.5%** | — |
| 字符错误率 | 0.743 | **0.209** | — |
| 指令残留率 | 31.9% | **0%** | ≤ 2% ✅ |
| 反例保留率 | 81.2% | **87.5%** | ≥ 95% ❌ |
| 新增数字率（clean） | 2.3% | 3.4% | ≤ 1% ❌ |
| 翻译 chrF | 39.5 | **60.2** | — |
| JSON 合法率 | 100% | 100% | 100% ✅ |
| 建议规则合规率 | 93.2% | **100%** | 100% ✅ |
| 建议条数一致率 | 18.2% | **81.8%** | — |
| 延迟中位数 | 0.86 s | 1.14 s（HF generate） | ≤ 1 s ❌ |

**结论**：

- 仅约 1200 条手写种子做 LoRA 微调，就让 2B 模型基本掌握了“执行内联指令并把指令词删掉”这一行为：指令残留率从 31.9% 降到 0%。
- 字符错误率降为原来的约 1/3.5，翻译 chrF 提高 20 分。
- 反例保留率仍未达标：模型仍会过度修改本该原样保留的句子。

### 6.2 部署格式对比（测试集 v1，同一模型 v1）

| 指标 | HF PyTorch（WSL） | GGUF Q8_0（llama.cpp） | GGUF Q4_K_M |
| --- | --- | --- | --- |
| 完全一致率 | 54.5% | 54.5% | 53.4% |
| 字符错误率 | 0.209 | 0.210 | 0.239 |
| 反例保留率 | 87.5% | 87.5% | 87.5% |
| 翻译 chrF | 60.2 | 58.9 | 63.8 |
| 延迟中位数 | 1.14 s | **0.14 s** | **0.13 s** |
| 显存占用 | 约 4.4 GB | 约 2.5 GB | 更低 |
| 服务启动 | 约 50 s（WSL Python 服务） | **约 4 s** | 约 4 s |

**结论**：

- Q8 量化后质量与原模型一致，延迟降为原来的约 1/8，显存减少约 45%，启动时间从 50 s 缩短到 4 s。
- Q4 质量略有下降，适合显存更紧张的设备。
- 默认使用 Q8。

- 针对单一能力加数据，没有明显损伤其他能力，但小测试集上的波动不小（±2 个百分点），需要更大的测试集才能判断细微差异。
- 反例保留率在三个版本中始终停在 87.5%，是当前最稳定的短板。

## 7. 问题与解决

### 7.1 训练

| 问题 | 原因 | 解决 | 结论 / 经验 |
| --- | --- | --- | --- |
| 训练启动报错，不认识 `warmup_ratio` | transformers v5 去掉了该参数 | 改为固定 `warmup_steps=20` | 新版本框架的 API 变动要先用冒烟训练（几十步）验证 |
| 6 GB 显存训练 OOM | 序列与批次占用超出显存 | batch 1 + 梯度累积 8；`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`；每 100 步存检查点，`--resume` 续训 | 2B bf16 LoRA 峰值 4.4 GB，在 6 GB 卡上余量很小 |
| v2 训练到第 269 步时中断：“No or negligible GPU memory available for fused cross entropy” | 训练期间用户打开了安卓模拟器、Steam、Discord 等占用显存的程序 | 关闭这些程序后从 checkpoint-200 续训 | 训练期间要独占 GPU；检查点间隔决定中断后损失多少进度 |
| 自建脚本 `inspect.py` 导致导入异常 | 与 Python 标准库 `inspect` 重名 | 改名 | 脚本命名不要与标准库冲突 |
| 模型输出 `<think>` 推理过程 | Qwen3.5 默认开启思考模式 | 训练与推理都在对话模板里设 `enable_thinking=False`；llama-server 用 `--chat-template-kwargs`；客户端额外剥离 `<think>` 块，兼容自定义推理模型 | 训练和推理的模板参数必须一致 |
| 是否用 QLoRA 省显存 | Unsloth 官方文档指出 Qwen3.5 的 4-bit 量化误差高于常规模型，不建议 QLoRA 训练（部分第三方教程仍推荐 QLoRA，以官方为准） | 改用 bf16 LoRA | 2B 模型 bf16 LoRA 在 6 GB 卡上可行；4B 在本机做 bf16 LoRA 大概率放不下，需要云端 GPU |

### 7.2 部署

| 问题 | 原因 | 解决 | 结论 / 经验 |
| --- | --- | --- | --- |
| 本地服务启动慢（约 50 s）、每句 1.0–1.8 s，而且运行时依赖 WSL | 最初用 WSL 里的 Python 服务加载“基座 + LoRA” | 合并 LoRA → GGUF → Windows 原生 llama-server | 见 §6.2：速度约快 8 倍，质量不变；训练仍留在 WSL |
| Qwen3.5 混合架构能否转换成 GGUF | 线性注意力层是较新的结构 | 固定 llama.cpp 版本 b11596，先在本机验证转换和推理 | 新架构要锁定运行时版本 |
| VoxFlow 崩溃后 llama-server 进程残留，继续占显存和端口 | 子进程不会随父进程退出 | Windows 作业对象（KILL_ON_JOB_CLOSE） | 已模拟崩溃验证，服务会跟着退出 |
| 长段口述的整理结果被截断，后半段丢失 | 固定的 max_tokens 不够 | max_tokens 按输入长度计算；`finish_reason == "length"` 时保留原文并提示 | 宁可不改，也不能丢内容 |
| 旧请求的结果覆盖了新内容 | 异步结果回来时会话已经变了 | 按会话号、用户是否编辑过、当前模式丢弃过期结果；建议延迟 1.2 s 再请求，用户先确认就不再请求 | 单线程执行器避免慢请求排在下一句前面 |
| 强制结束 VoxFlow 后语音识别子进程残留（约 370 MB） | llama-server 已用作业对象托管，但 ProcessPoolExecutor 的子进程没有 | 主进程启动时把自己加入“关闭即结束”的作业对象，子进程自动继承 | 打包测试时发现；所有子进程都应随主进程结束 |
| 重训期间应用找不到模型 | 旧模型移到 archive 后，新模型还没导出 | 模型发现时扫描 archive 目录（标为“旧版”，最新的优先）；保存的模型文件缺失时自动回退到可用模型 | 版本迭代时要保证始终有可用模型 |

## 8. 主要结论

1. **小模型加少量高质量数据可行**：2B 模型用约 1200 条手写种子加约 1800 条程序扩增做 LoRA 微调，就能在 6 GB 笔记本 GPU 上学会口语清理、回头编辑和内联指令执行。指令残留从 31.9% 降到 0%，字符错误率从 0.74 降到 0.21。
2. **部署格式决定可用性**：GGUF Q8 + llama.cpp 质量不变，单句延迟从 1.14 s 降到 0.14 s，显存降到 2.5 GB，启动 4 s，满足“说完即整理”的交互要求。
3. **格式规则易学，知识型能力难补**：名姓顺序约 40 条样本就学会了；拼音准确率需要更多样本，提升也有上限（未见名字 42% → 75%）。
4. **手写种子是数据质量的关键**：回头编辑、隐含理由这类样本无法靠模板生成；同时要避免名人和带性别推断的样本。
5. **过度修改是主要短板**：反例保留率在三个版本中都是 87.5%，没有达到 95% 的目标。

## 9. 局限与后续改进

| 方向 | 具体措施 |
| --- | --- |
| 评估 | 扩大测试集（至少几百条），加入人工盲评（建议有用性 50 条、翻译 30 条），并用真实录音建立中英混说的 ASR 基准 |
| 数据 | 补充反例（目标保留率 95%）、隐式修正、删除指令、时间推算、委婉改写不编造理由等样本 |
| 人名 | 在模型外用拼音库预先转写中文人名，或在提示中提供拼音参考 |
| 模型 | 训练并对比 Qwen3.5-4B；语音识别候选 Qwen3-ASR 0.6B / 1.7B，需用真实录音对比 SenseVoice |
| 产品 | 意图识别、安装包、真实用户试用数据（需先和用户确认隐私边界） |
