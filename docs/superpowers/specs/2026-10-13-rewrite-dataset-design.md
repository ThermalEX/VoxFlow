# 口语改写模型数据集设计

日期：2026-10-13
状态：设计已确认，待实施计划

## 1. 背景与目标

VoxFlow 目前只完成 ASR → 预览 → 上屏。下一阶段加入“智能输入”：识别结果经过一个本地小模型改写后再上屏。本设计只覆盖**数据集**（以及组装、校验它的脚本）；模型训练、评估脚本与接入软件是后续独立的工作。

产品交互分两步：

1. **说话时**：用户可在语音里直接带指令（翻译、正式一点、委婉一点……），指令可前置、后置或在句中。没有指令时只做清理。
2. **说完后**：软件在后台自动给出若干条自由生成的改写建议，用户可选用。

约束：

- 改写模型**本地优先，可选云端**；微调只针对本地模型。
- 目标硬件：RTX 3060 Laptop，6 GB 显存，32 GB 内存。本地模型规模 1.5B–4B，倾向 Qwen3-1.7B / Qwen3-4B（Apache 2.0），训练阶段再核实最新同级模型后定稿。Qwen3 需关闭思考模式。
- 数据集与具体模型无关，导出通用 chat messages JSONL。
- 数据由 Claude 在对话中手写种子，程序只做简单噪声扩增；数据均为合成内容，不含用户真实数据，可入库。

## 2. 方案

**一个模型、两个任务**，以不同系统提示区分，共用一个 LoRA：

- **任务 1 `clean`（清理并执行）**：输入原始 ASR 文本，输出最终上屏文本。
- **任务 2 `suggest`（自由建议）**：输入任务 1 的结果，输出 0–3 条建议的 JSON 数组。

运行时先跑任务 1 并立即可上屏；任务 2 在后台生成，不阻塞上屏。

未采用：两个任务各训一个 LoRA（维护和显存成本高）；规则清理 + 模型只改写（回头编辑用规则写不可靠）。

## 3. 任务 1 覆盖类别

| # | 类别标识 | 说明 | 示例输入 → 输出 |
| --- | --- | --- | --- |
| 1 | `filler` | 口气词、填充词（含英文 um/uh/like/you know） | “额，那个，就是我明天请个假啊” → “我明天请个假。” |
| 2 | `repetition` | 重复、口吃 | “我我我觉得这个这个方案可以” → “我觉得这个方案可以。” |
| 3 | `immediate_correction` | 即时纠正 | “周五，不对，周六开会” → “周六开会。” |
| 4 | `edit_delete` | 回头编辑：删除 | “我今天要买苹果，梨子，哦昨天买过苹果了，去掉苹果” → “我今天要买梨子。” |
| 5 | `edit_replace` | 回头编辑：替换 | “帮我约张三吃饭，把张三换成李四” → “帮我约李四吃饭。” |
| 6 | `edit_insert` | 回头编辑：补充 | “买牛奶和面包，哦还有鸡蛋” → “买牛奶、面包和鸡蛋。” |
| 7 | `implicit_reason` | 带理由的隐式修正 | “订周二的票，哦周二我有课，那就周三吧” → “订周三的票。” |
| 8 | `spoken_format` | 口述格式：“第一……第二……”成编号列表；“换行”“逗号”等口述标点 | |
| 9 | `instr_translate` | 内联指令：中译英、英译中 | “明天下午开会，翻译成英文” → “There's a meeting tomorrow afternoon.” |
| 10 | `instr_style` | 内联指令：正式、委婉、简洁、口语、礼貌等 | |
| 11 | `instr_combo` | 指令与编辑组合：先应用编辑，再执行指令 | |
| 12 | `neg_instruction_like` | 反例：像指令的正文，原样保留 | “他让我把这段翻译成英文” |
| 13 | `neg_code_switch` | 反例：中英混说照常保留，不擅自翻译 | “这个 PR 帮我 review 一下” |
| 14 | `neg_clean` | 反例：已经干净的句子原样输出 | |

指令位置（第 9–11 类）：前置与后置约各半，另有少量句中。每条样本记录 `instr_position`：`prefix` / `suffix` / `infix`。

一条样本可同时属于多个类别（如 `edit_delete` + `implicit_reason`）。

**不做**：同音错字纠正（如“机器学系”→“机器学习”），小模型易编造内容，留待后续版本。

## 4. 任务 2 规则

输入为任务 1 的最终文本；输出为 JSON 数组，每项 `{"label": str, "text": str}`。

```json
输入：明天的会我去不了了，你们先开吧。
输出：[
  {"label": "更礼貌", "text": "不好意思，明天的会我临时有事去不了，大家先开，会后我再看纪要。"},
  {"label": "说明原因", "text": "明天我要去客户那边，会议参加不了，你们先开，有需要我配合的随时说。"},
  {"label": "译成英文", "text": "I can't make it to tomorrow's meeting — please go ahead without me."}
]
```

1. **自由方向**：按内容与场景选最有用的改写方向，不限类别。
2. **实质区别**：建议之间、建议与原文之间不能只差一两个字。
3. **不改事实**：不编造原文没有的人名、时间、数字。需要补充信息的方向（如“说明原因”）只在补充内容是通用、无具体事实时才可给出；否则不给该方向。
4. **可少给**：“好的”“收到”等短句给 1 条或 `[]`。
5. **标签语言跟随原文**，长度不超过约 6 个汉字或 3 个英文单词。
6. **场景多样**：工作群消息、邮件、家人朋友聊天、客服售后、购物、日程、技术开发、学校学习、社交媒体发帖等。

## 5. 文件与格式

```
training/rewrite/
  prompts.py              两个任务的系统提示（训练与运行时共用）
  seeds/
    clean_cases.jsonl     任务 1 手写样本
    suggestions.jsonl     任务 2 手写样本
  build_dataset.py        校验、扩增、划分、导出、覆盖报告
  build/                  train/valid/test.jsonl（.gitignore，可重新生成）
tests/test_rewrite_dataset.py
```

种子记录：

```json
{"id": "edit-del-0001", "categories": ["edit_delete", "implicit_reason"], "scene": "shopping",
 "raw": "我今天要买苹果，梨子，哦昨天买过苹果了，去掉苹果", "output": "我今天要买梨子。"}
{"id": "sug-0001", "scene": "work_chat", "input": "明天的会我去不了了，你们先开吧。",
 "suggestions": [{"label": "更礼貌", "text": "……"}]}
```

指令类样本另含 `instr_position`。

导出格式（每行一条）：

```json
{"messages": [{"role": "system", "content": "…"}, {"role": "user", "content": "…"}, {"role": "assistant", "content": "…"}],
 "meta": {"id": "…", "task": "clean|suggest", "categories": ["…"], "source": "hand|augmented"}}
```

任务 2 的 assistant 内容为紧凑 JSON 字符串（`ensure_ascii=False`）。

## 6. 规模与划分

| 部分 | 计划数量 | 组成 |
| --- | --- | --- |
| 任务 1 手写 | ~900 | 编辑/改口（3–7 类）~250；指令 ~300（翻译 ~120 含双向，风格 ~140，组合 ~40）；口述格式 ~60；反例 ~150；口气词/重复自然样本 ~100 |
| 任务 2 手写 | ~400 | 其中 ~40 条为少给或 `[]` |
| 任务 1 程序扩增 | ~1800 | 以手写样本中的干净文本为底，注入口气词、重复、模板化即时纠正；标准答案为原干净文本 |
| 合计 | ~3100 | 扩增占比不超过 60% |

划分：按种子分组，训练 85% / 验证 5% / 测试 10%；扩增变体随其种子归组，杜绝泄漏。测试集只含手写样本。划分用固定随机种子，可复现。

## 7. 校验与质量把关

构建失败条件：

- 字段缺失或类型错误；`id` 重复；类别标识不在第 3 节列表内。
- 任务 2：建议条数不在 0–3；标签超长；建议之间或与原文完全相同。
- 反例（12–14 类）输出与输入在忽略标点和空白后不一致。
- 任务 1 非反例输出残留指令词（翻译成、正式一点、去掉、换成……）。

覆盖报告：按类别、场景、语言、指令位置统计；低于第 6 节计划下限时给出警告（不失败，便于分批写作）。

近似去重：种子之间字符 n-gram 相似度过高时警告。

**分批写作与风格校准**：第一批每类约 10 条（共约 150 条）交用户抽查，确认清理尺度（如是否保留“吧、呢”）、正式程度、建议长度后，再写其余部分。之后每批约 50 条，写完即跑校验。

## 8. 模型评估标准（训练阶段使用）

| 指标 | 任务 | 计算 | 目标 |
| --- | --- | --- | --- |
| 反例原样保留率 | 1 | 12–14 类输出与输入一致（忽略标点） | ≥ 95% |
| 指令残留率 | 1 | 输出含指令词 | ≤ 2% |
| 分类别准确率 | 1 | 规范化后完全一致 + 字符编辑距离 | 横向对比 |
| 翻译质量 | 1 | 与参考译文的 chrF，加人工 30 条 | 横向对比 |
| 事实保持 | 1、2 | 输出出现输入中没有的数字、英文专名、人名 | 任务 1 ≤ 1%；任务 2 人工复核 |
| JSON 合法率 | 2 | 可解析、条数 0–3、标签合规 | 100% |
| 建议区分度 | 2 | 建议间及与原文的相似度 | 横向对比 |
| 建议有用性 | 2 | 盲评 50 条“会用/不会用” | 横向对比 |
| 延迟 | 1 | RTX 3060 上 ≤ 50 字句子 | 中位数 ≤ 1 s |

对照组：未微调原始模型（仅提示词）、微调后模型、可选云端大模型上限。1.7B 与 4B 均评估后再决定两任务是否共用模型。

真实语料：训练阶段由用户录制 20–30 段真实口语，经 SenseVoice 转写为文字作为小型真实测试集；录音不入库，仅保留文字。
